Abstract

Tackling complex real-world tasks can exceed the capabilities of a single large language model (LLM), motivating the use of multi-agent workflows that coordinate specialized agents to work together on these tasks. Recent methods train LLMs to construct better workflows from execution outcomes, but they optimize only the workflow generator, while the other agents that build or execute each workflow remain fixed even though every outcome depends on all of them. However, extending training beyond the generator is challenging: the agents are coupled, and a workflow's outcome is a single sparse score that cannot tell which agent causes a failure. We propose FloWright, which leverages the workflow as a harness to optimize workflows. By introducing a hierarchical, structure-aware reward paradigm, FloWright enables one role to self-evolve and two or more roles to co-evolve, with no additional models, labels, or executions. Considering the limitation that workflows are commonly trained and evaluated on data that a single agent can already handle, we further propose DataWright, an adaptive data hardening approach that converts existing datasets into workflow-level tasks with increased difficulty. Across document, slide, chart, code, math, and finance tasks, small open models trained with FloWright achieve improved performance by up to ↑7.41%, with co-evolving (↑5.03%) more roles gaining more than optimizing one of them alone (↑2.83%).

What Limits Workflow Optimization?

Recent work trains LLMs to construct better workflows from the outcomes of executing them. Yet these methods typically optimize a single workflow generator. Because the outcome of a workflow depends jointly on every agent that builds or executes it, training only the generator leaves the other agents shaping every outcome without ever learning from it.

Only the Generator Learns

The agents that execute a workflow, and any others that help build it, remain fixed, which limits how much the workflow as a whole can improve.

Agents Are Coupled

One agent's output becomes another's input. Training agents separately ignores how each agent's behavior shapes what the others learn.

The Outcome Is One Sparse Score

A single score for the whole workflow cannot tell which agent causes a failure, and existing attribution adds costly models, labels, or executions.

FloWright: Learning to Wright Workflows

A complex task x is solved by a workflow, a directed graph G = (V, E) whose nodes are agents, tools, or skills, and whose edges carry the data and control flow among them. Upstream, the Generator πg produces G. Downstream, the harness H executes and grades it:

x →πg G →H (y, h(G, x)),    h(G, x) ∈ [0, 1]

The signal h serves three purposes: the evaluation metric, the training signal, and the test-time objective.

Hierarchical Structure-Aware Reward Ladder

The harness does not reduce an execution to a single pass-or-fail outcome. It stages the signal into a ladder of auto-verified terms, so the policy sees a meaningful gradient even when the workflow falls short. Every optimizable role ρ instantiates its own reward from the same shared harness:

hρ = wf f + wv vρ + we e + wa a + wc cρ

Format (f)

Whether the role's own output parses. An output that cannot be read leaves nothing to execute.

Validity (vρ)

Whether the role's contribution is valid, such as a workflow that is a well-formed graph over the pool. Deterministic, never a learned judge.

Execution (e)

Whether the workflow executes to a final answer.

Answer (a)

How correct that answer is, shared by every role.

Credit (cρ)

The fraction of the role's own nodes that root-cause a failure, read from the execution trace the harness already records.

cρ = − |Fρ| / |Vρ| ∈ [−1, 0]
  • From the role's own output to the task outcome: the four staged terms measure how far a workflow reaches.
  • From local to global: the credit term charges each role only for the failures of the nodes it authors, with no additional execution and no new signal.
  • Only genuine root causes are charged: a cascaded failure propagates to its root along the workflow's edges, and infrastructure faults are excluded.

Wire the Workflow: Topology and Pools

Upstream construction turns on three choices: the topology of the workflow, and the granularity and dynamics of the pool it draws from. A single workflow can express sequential, parallel, branching, and iterative structure as the task demands.

Four Topologies, One Executable Graph

The four topologies differ only in where the control flow is written down. Each is converted into the same directed graph, so execution, credit, and evaluation never observe which topology produced it.

Schema: Steps With Dependencies

Steps declare their dependencies, and one control_flow block states the control flow.

{"steps": [{"step_id": "step_1", "agent": "Visual Analyst",
            "instruction": "Analyze the images for Question 1 [...] return only the letter",
            "inputs": {"image_1.jpg": [...]}, "outputs": ["Answer_Q1"], "depends_on": []},
           [...]],
 "control_flow": {"type": "sequential", "loop_steps": [], "max_iterations": null}}

Graph: Typed Edges

Agent nodes are connected by typed edges that carry the control flow.

{"agents": [{"agent_id": "visual_analyst_agent", "agent": "visual_analyst_agent",
             "instruction": "Analyze the images to answer three questions [...]",
             "inputs": [...], "outputs": ["Answer_Q1", "Answer_Q2", "Answer_Q3"]}],
 "flows": [{"source": "visual_analyst_agent", "target": "visual_analyst_agent",
            "type": "sequence", "condition": "true", "max_iterations": 1}]}

State Machine: Conditioned Transitions

States are linked by transitions that carry conditions and bounds.

{"states": [{"state_id": "Q1_Analysis", "agent": "VisualDataAnalyzer",
             "action": "Analyze [...] select the correct option letter",
             "outputs": ["Answer for Question 1"]}, [...]],
 "transitions": [{"from_state": "Q1_Analysis", "to_state": "Q2_Analysis",
                  "condition": "answer is a single letter", "max_iterations": 3}, [...]],
 "start_state": "Q1_Analysis", "terminal_states": ["Final_Aggregation"]}

Code: Typed Blocks

Blocks carry the control flow in their type.

{"program": {"language": "workflow_pseudocode",
             "blocks": [{"block_id": "block_1", "type": "step", "agent": "visual_analyst",
                         "instruction": "Analyze the chart and the crop [...] return the option letter",
                         "outputs": ["Answer_Q1"], "depends_on": [], "condition": null,
                         "max_iterations": 3}, [...]]}}

Pool Granularity and Dynamics

Modular Pool

Agents, tools, and skills stay separate units, enabling flexible selection and composition.

Ω = Ωagent ∪ Ωtool ∪ Ωskill

Capsule Pool

Each agent is bundled with the tools and skills it needs into a self-contained capsule.

Ω = Ωcapsule

Dynamic Pool

When a task calls for a capability the pool does not contain, the Generator's Inventor skill expands the pool with the missing tool, skill, or agent. A grown pool also carries components distilled from past experiences.

One Harness, Four Evolution Modes

The reward paradigm serves every role from one shared harness, enabling one role to self-evolve or several to co-evolve. When several roles train inside one harness, each role's behavior shapes what the others encounter: the coupling is a mutual curriculum.

(a) Single-Role Self-Evolution

One role optimizes its role-specific reward inside the harness as it runs, so it evolves in the same flow that will use it.

(b) Agent-Skill Co-Evolution

An agent co-evolves with its own skill, such as the Generator with its Inventor skill.

(c) Upstream-Downstream Co-Evolution

An upstream agent that builds the workflow is coupled with a downstream agent that executes it.

(d) Multi-Agent Co-Evolution

Any two or more agents co-train, each learning against the latest evolved policies of the others.

Train-Time Reinforcement, Test-Time Distillation

Train Time: Maximizing the Signal

A role's policy is optimized to maximize its expected signal over tasks. FloWright contributes a training paradigm rather than an optimizer, so GRPO, DAPO, and CISPO all instantiate it.

J(πρ) = E [ hρ(G, x) ]

Test Time: Meta Distillation

With no weights changing, the harness distills a reusable prior, internally from its own experiences or externally from a stronger teacher, and distills successful experiences into few-shot cases.

P* = arg maxP E [ h(G, x | P) ]

DataWright: Workflow-Level Data Hardening

Datasets that a single agent can already handle can neither reveal nor optimize what a workflow adds beyond it. DataWright converts existing datasets into workflow-level tasks by rule, with no model in the loop. Hardening changes how hard a task is, not how its answers are graded: every sub-question keeps the metric of its own answer type, and a task's score is the mean over its sub-questions.

Three Hardening Strategies

Shared: Decomposition

Bundles ℓ questions about the same input into one task, which splits into sub-questions that can be assigned and answered separately.

Paired: Routing

Bundles ℓ questions, each with its own distinct input, into one task. Each sub-question is matched to the input that answers it.

Decoy: Localization

Keeps one question and places its input among ℓ − 1 decoy inputs drawn from the same dataset.

  • In-distribution (4 arms): the four training datasets at the paired strategy and ℓ = 3.
  • Out-of-distribution (13 arms): the same four datasets under a strategy, a level, or both that training never sees.
  • Out-of-domain (27 arms): eight datasets FloWright never trains on.

  • Workflows beat a single agent: untrained FloWright improves over the single-agent baselines by at least ↑11.39% overall.
  • Every evolution mode helps in every regime: at matched model size, each mode exceeds its untrained counterpart, by up to ↑7.41%.
  • Co-evolving more roles gains more: multi-agent co-evolution leads 7 of 8 columns and gains ↑5.03% overall, ahead of ↑4.06% (agent-skill), ↑3.06% (upstream-downstream), and ↑2.83% (single role).

Gains hold on every dataset, strategy, and level

Under multi-agent co-evolution, all 12 datasets gain over the untrained workflow, by up to ↑7.34% on LongDocURL and ↑5.13% on ChartCoder.

The gain grows as the strategy demands more of the workflow: ↑3.57% on shared, ↑4.11% on paired, and ↑4.68% on decoy.

A reusable prior helps with weights fixed

Distilling the prior from the system's own experiences gains ↑0.93% overall, and from a stronger teacher ↑1.10%.

Meta distillation gives the largest test-time gain, up to ↑2.58% at five shots.

Composed with train-time evolution, it reaches ↑3.21% overall.

Generalizability: Algorithms, Rewards, Topologies, and Pools

The gains hold across RL algorithms, reward terms, workflow topologies, pool granularities, and pool dynamics.

The signal generalizes across RL algorithms

Optimizing the Generator outperforms the untrained baseline under every algorithm: ↑2.83% for GRPO, ↑3.23% for CISPO, and ↑3.84% for DAPO overall.

DAPO leads in every regime, and its margin widens out-of-domain.

Every layer of the ladder contributes

Grading format and answer alone stays close to the untrained baseline. Validity contributes the largest single increment: ↑2.07% under GRPO and ↑2.29% under DAPO.

The structure-aware credit adds a further ↑0.69% and ↑0.75%.

Gains hold whichever topology is written

Optimization improves every topology: ↑2.83% for schema, ↑2.62% for state machine, ↑1.74% for code, and ↑1.25% for graph.

Code leads both untrained (34.12%) and with an optimized Generator (35.86%).

Capsules lead, and optimization narrows the gap

Bundling each agent with the tools and skills it needs gains ↑3.83% on Qwen3.5-4B and ↑3.87% on Qwen3.5-9B over a modular pool.

Optimizing the Generator improves the modular pool by ↑4.50% against ↑2.83% for capsules.

Growing the pool from successes adds the most

A pool that grows on demand gains ↑4.83% over a pool held fixed, the largest effect among the single design choices.

Distilling past experiences into the pool adds a further ↑1.44% when only successful ones are kept, against ↑0.53% when failed ones are kept too.

Transferability: Across Roles and Backbones

What FloWright optimizes transfers across roles and to backbones it never trains alongside, at both train and test time.

Whichever role is optimized, it helps

Alone, the Generator gains ↑2.83%, the Inventor skill ↑0.90%, and the downstream agent ↑0.88%.

Co-evolution gains more: ↑4.06% for Generator and skill, ↑3.06% for upstream and downstream, and ↑5.03% for multi-agent.

Gains transfer to other backbones

With the other roles on Qwen3.5-9B, an optimized 4B role exceeds the all-9B baseline of 47.50%: 47.67% for the Generator, 47.96% for the Inventor skill, and 48.50% for both.

The downstream agent bounds what a workflow performs, however well it is built.

The prior helps models it never trains

A meta-distilled prior gains ↑1.62% on Qwen3.5-4B, ↑1.53% on Qwen3.5-9B, ↑1.44% on GPT-5-mini, and ↑1.91% on GPT-5.4-mini.

Every backbone keeps its weights fixed, so each gain comes from the prior alone.
